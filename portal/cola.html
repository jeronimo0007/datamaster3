Defesa — por que Kafka e Rabbit? (se a banca apertar)

Não diga: “usei os dois para estudar.”
Diga: problemas diferentes → ferramentas diferentes.
  • Kafka = fato (“a análise aconteceu”) — log, volume, replay, vários consumidores, categoria para Negócios.
  • Rabbit = tarefa (“envie o e-mail”) — work queue pontual; HTTP não espera SMTP.

Poderia só Kafka? Sim — consumer manda SMTP. Trade-off: overkill para alerta; misturam fato e tarefa; no cloud o par natural de e-mail é Kafka/SQS.

Poderia só Rabbit? Sim para e-mail. Trade-off: fraco como log de negócio com replay → lake/Gold.

Fala 10: “Eu poderia unificar. Separarei porque Kafka registra o fato e Rabbit executa a tarefa. Só Kafka deixa o alerta mais pesado; só Rabbit deixa fraco o barramento analítico. No cloud: Kafka + Kafka — o porquê é o mesmo.”

Defesa — Kafka igual nos três ambientes (tópico 2)

Subo Kafka em qualquer ambiente — local, Azure e AWS — sem trocar por “serviço equivalente”.
  • Local / Docker: Kafka — broker que eu opero no Compose.
  • Azure: Kafka — mesmo broker em Container Instances (ACI), mesmo contrato.
  • AWS: Kafka + Mongo + Airflow no ECS — mesma stack, lake no S3.

Fala 10: “Kafka é o padrão de log de eventos. Uso Kafka na mesa e o mesmo Kafka na nuvem — o contrato não muda (partições, consumer groups, replay). Um desenho, três lugares: Kafka = Kafka, MongoDB = MongoDB.”

Defesa — por que equivalência Monitor/CloudWatch (e não “só Prom/Grafana na nuvem”)?
  • Prometheus pode na nuvem (Azure/AWS Managed Prometheus + Managed Grafana).
  • Métrica de PaaS (Kafka, MongoDB, Databricks, Kafka) não vem de scrape da minha app — só existe no Monitor/CloudWatch.
  • Equivalência = capacidade / papel, não “proibido usar Prometheus”.
  • Produção ideal: híbrido — Prom para app/K8s; nativo para PaaS; Grafana como visão única (datasource Azure Monitor/CW).

Fala: “Na mesa não existe Azure Monitor; Prometheus prova o pilar de métricas. Na nuvem mantenho o padrão aberto na app e uso o nativo para plataforma. O SLI é o mesmo.”

Dynatrace / Datadog / New Relic? APM completo (métricas+traces+AIOps). Custo/lock. Equivalente no mapa: App Insights / X-Ray.

Kibana / ELK? Forte em logs/busca — não substitui Prometheus para SLO. Mesa: docker logs; nuvem: Log Analytics.

Por que não só Grafana? Grafana visualiza; precisa de fonte (Prometheus).

Tracing na mesa? NÃO — mesa = métricas. Tracing distribuído = App Insights / X-Ray (nuvem). Não afirmar APM no Compose.

SLIs (decore os 3):

  • Latência do /analyze (meta <2s)
  • Disponibilidade — /health / target UP
  • Taxa de erro (falhas vs sucesso)

SLO = meta (99,9%) · SLI = indicador medido.

Classes (não misturar): Dynatrace = APM completo (≈ App Insights) · Kibana = logs/busca (≈ Log Analytics) · Prometheus = métricas · Grafana = visualização. Dynatrace não é “Kibana e mais” — famílias diferentes.

Q: “Você usa TLS no Kafka?”

Resposta: “Não. Na mesa o listener é PLAINTEXT em rede Docker interna (kafka:29092), sem exposição pública. Em produção, criptografia em trânsito é obrigatória e o padrão muda:”

Fecho: “E tem um ponto de LGPD junto: o evento leva CPF e só o final do cartão. Em produção o CPF vai tokenizado, com retenção curta no tópico e o histórico longo no lake governado.”

Q: “E OAuth2 / JWT? Como autentica quem chama a API?”
  • Mesa: perfil local com Spring Security em permitAll — deliberado, para a banca chamar o curl sem fricção.
  • No código já existe o hook: perfil enterprise com oauth2ResourceServer(jwt) e /api/v1/** autenticado (SecurityConfig.java). É esqueleto, não um IdP configurado — não invento issuer.
  • Padrão de produção: API é resource server. Valida JWT assinado (RS256) contra o JWKS do Entra ID / Cognito: iss, aud, exp, assinatura e scope.
Quem chamaFluxo OAuth2Por quê
Sistema → API (core, batch)Client CredentialsM2M, sem usuário; identidade da aplicação
Front SPA / analistaAuthorization Code + PKCENunca segredo no browser
Parceiro externomTLS + client credentialsDupla prova de identidade

Scopes por papel (least privilege): fraud.score:write (chamar /analyze) · fraud.read (consultar) · fraud.admin (liberar/bloquear) · pii.read separado — ver PII em claro é escopo próprio e auditado.

Por que JWT e não API key? Key é segredo estático, sem expiração, sem escopo, sem identidade. JWT expira, carrega escopo/claims, é revogável no IdP e dá auditoria de quem chamou.

Q: “Como o seu front acessa a API?”
  • Mesa — honestidade: o portal (:8880) faz fetch do browser direto na API :8080, com @CrossOrigin("*"). O Streamlit (:8501) chama server-side via API_URL=http://api:8080 na rede interna.
  • Risco que eu mesmo aponto: CORS * + sem token = qualquer origem chama. Aceitável em lab, não em produção.
  • Produção: browser não fala com a API core. Fluxo: Front → Front Door/WAF → API Gateway (valida JWT) → API core em rede privada. CORS restrito à origem do app; token no header Authorization; nada de PII em query string (query vai para log de acesso).
  • O padrão do Streamlit — chamada server-side — já é o correto: o segredo fica no servidor, não no browser.

Q: “Como é o acesso a Bronze / Silver / Gold?”

Mesa: MinIO com credencial única de laboratório (minioadmin) e buckets bronze/silver/gold criados no minio-init. Sem policy por camada — assumo.

Produção — identidade por workload, nunca chave compartilhada:

Frase de ouro: “O Medallion não é só qualidade de dado — é também fronteira de segurança. Quem lê a Gold nunca deveria conseguir ler a Bronze. Analista de negócio não precisa de CPF; precisa de fraude por categoria.”

  • Não há segredo real versionado: .gitignore bloqueia .env, secrets/, *.pem, *.key, tfstate. Chave de API externa vem por variável de ambiente.

Armadilha clássica: “criptografei o disco, então estou LGPD.” → Não. Operador ainda vê PII em claro na API. Crypto e máscara resolvem problemas diferentes.

Armadilha 2: “mascarei = anonimizei.” → Não. Máscara ainda permite reidentificação parcial; anonimização exige irreversibilidade.

Armadilha 3 (SHA / “cripto irreversível”): Hash ≠ criptografia. SHA-1/SHA-256/bcrypt = função de hash (mão única) — valida/compara, não descriptografa. Criptografia (AES, RSA…) = sempre pensada para reverter com a chave. Se a banca falar “criptografia irreversível”, corrija: “isso é hash, não crypto.”

FamíliaReversível?ExemplosUso
CriptografiaSim (com chave)AES, TLS, RSAProteger em trânsito/repouso e recuperar depois
HashNão (por desenho)SHA-256, bcrypt, HMACIntegridade, senha, dedupe, anonimização analítica
Hash + saltNão (melhor)sha256(cpf + salt)Dificulta rainbow table; ainda é pseudônimo forte se o universo for pequeno

Fala: “SHA não é criptografia irreversível — é hash. Criptografia eu recupero com a chave; hash eu só comparo o digest.”

  • POST /api/v1/lgpd/mask = prova para a banca sem depender da UI.

Campos: CPF · e-mail · telefone · nome · cartão (só final visível) — PII típica de canal.

Postura honesta (se perguntarem “provou 10M?”)

“Não. Dez milhões/dia é capacidade-alvo do desenho. Na mesa mostro o caminho e onde puxo a alavanca em cada camada — não um load test de produção.”

Mantra: “Réplica sem partição/chave certa não remove gargalo.”

Por quê escalar por camada (e não “só subir a VM”)
  • Vertical (máquina maior) — limite rápido, ponto único.
  • Horizontal — mais réplicas/partições; precisa API stateless + chave de partição boa.
  • Separar batch do online — job Spark não pode competir com o path <2s.
  • FinOps — custo por 1M tx; escala sem controle quebra o negócio.

Gargalos típicos: hot key no perfil · consumer lag · I/O do lake mal particionado.

Fala (~25 s)

“Escalo por camada: partições no stream, workers no Spark, RU no serving, réplicas na API. A meta de dez milhões/dia é do desenho — na mesa mostro o caminho e onde puxaria a alavanca. Sem particionamento certo, réplica a mais não resolve.”
