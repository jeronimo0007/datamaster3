✅ Etapa 1 · Extração de dados

Da fonte ao barramento

  • Por quê: fontes heterogêneas quebram o modelo se o schema do core for acoplado — preciso de contrato canônico + adapters.
  • Scripts Python (multi-fonte): generate_data.py + console :3333 simulam o core; transaction_adapters.py normaliza simulador, fila (Kafka / Kafka) ou CSV para o dicionário do modelo.
  • Kafka Producer: publicação com metadados e particionamento — AWS: Kafka / MSK. Repo: event_hub_producer.py.
  • ADF / Glue: orquestra cópia e landing em ADLS / S3 (secrets no Key Vault / Secrets Manager). Trade-off: schema registry (Avro) = mais governança, overhead no POC.

✅ Etapa 2 · Ingestão de dados

Streaming Kafka e batch Medallion

  • Por quê dois modos: stream resolve latência (<2s); batch resolve histórico, reprocessamento e perfis. Só batch perde tempo real; só stream (Kappa) encarece features históricas.
  • Streaming — Kafka (Kafka / MSK) · local Kafka: após o /analyze, a API publica o fato transaction-analyzed de forma assíncrona (categoria, CPF, card_last4) — o HTTP não espera o broker.
  • Batch — ADF / Glue + batch_dataprep_mongo.py: agrega histórico → MongoDB/Mongo para a API consultar online.
  • Medallion + Kafka: speed (API + evento Kafka) + batch (lake + perfis). Kafka é barramento/replay — o histórico definitivo para Negócios fica no lake/Gold (não retenção infinita no broker).

✅ Etapa 3 · Armazenamento (detalhe)

Camadas do lake, warehouse e operacional

BRONZE landing — JSON/CSV/Parquet bruto · schema-on-read · custo baixo SILVER refinado — limpeza, dedup, DQ (notebook: clean + enrich) GOLD consumo — features ML / KPIs (notebook: wide table transactions_ml) mesmo padrão de pastas: ADLS Gen2 (S3) …/bronze|silver|gold
  • Por quê duas camadas de armazenamento: lake = histórico/reprocessar; Mongo = serving online — cada carga tem seu storage certo.
  • Medallion: medallion_job.py (bronze → dq → silver → gold) · Airflow — Bronze intacto → Silver harmonizado → Gold ML.
  • DW Kimball: Synapse / Redshift — fato + dimensões para BI (narrativa).
  • MongoDB: user_profiles para /analyze — serving online de perfil de risco.
  • MongoDB (perfis): pré-agregado no batch (histórico) e consultado pela API em tempo real.
  • Trade-off: lake em ADLS/S3/MinIO para histórico e ML; Mongo para latência do score — cada um no seu papel.

✅ Etapa 4 · Observabilidade

Telemetria de ponta a ponta

  • Por quê: sem métricas não cumpro SLO de latência (<2s) nem detecto regressão. Separar coleta, visualização, logs e traces.
  • Mesa: Prometheus (pull Actuator) + Grafana. Azure: Monitor + App Insights · AWS: CloudWatch + X-Ray — equivalência de capacidade, não proibição de Prometheus gerenciado.
  • SLI: disponibilidade /health, latência do /analyze, taxa de erro / target UP.
  • Logs: mesa docker logs · nuvem Log Analytics / Logs Insights. APM comercial (Dynatrace etc.) = mesma classe do App Insights.

✅ Etapa 5 · Segurança de dados

Defesa em profundidade: Azure (Azure)

  • Por quê defesa em profundidade: PII + decisão sensível — credencial no código ou storage aberto = incidente.
  • Crypto + Key Vault / KMS: TLS e CMK; secrets fora do código, com rotação e identidade gerenciada (IAM roles).
  • Entra ID / IAM + RBAC: least privilege por workload; lake com ABAC / Lake Formation; auditoria (CloudTrail).
  • Borda — APIM / API Gateway: TLS, OAuth2/JWT, rate limit e WAF na borda; a API core fica em rede privada, sem rota direta do browser.
  • Medallion como fronteira: identidade por job — quem lê a Gold não lê a Bronze; Gold agregada, sem PII.
  • Honestidade: na mesa mostro a camada de aplicação (API + DataMasker). Vault/IdP/TLS = desenho Terraform / nuvem — não overclaim no Compose.

✅ Etapa 6 · Mascaramento de dados

DataMasker e conformidade LGPD

  • Por quê: antifraude precisa de sinal — não de CPF/e-mail/cartão em claro na tela ou no log.
  • DataMasker + POST /api/v1/lgpd/mask: CPF, e-mail, telefone, nome, cartão — um controle na borda da API.
  • Três conceitos: mascaramento (UI) ≠ anonimização (irreversível) ≠ criptografia (reversível com chave).
  • LGPD: minimização e finalidade; hash+salt no código para narrativa de analytics sem vínculo.

✅ Etapa 7 · Arquitetura de dados

Modelo analítico e features

  • Por quê Medallion: qualidade progressiva + Bronze intacto para reprocessar — engenharia do lake (Databricks / EMR + Delta).
  • Por quê Kimball: BI pensa em fato + dimensões — Synapse / Redshift. Medallion ≠ Kimball (pipeline vs modelo dimensional).
  • Features online: user_profiles no Mongo / MongoDB — API não faz full scan no lake a cada tx. Gold = retreino; perfil = /analyze.
  • Governança: governanca.yaml + /data-quality/report + notebook DQ.

✅ Etapa 8 · Escalabilidade

Pronto para crescimento

  • Por quê por camada: réplica sem partição certa não resolve — stream, batch, serving e API têm alavancas diferentes.
  • Alavancas: partições Kafka/Kafka · workers Databricks/EMR · RU/s MongoDB/MongoDB · réplicas AKS/ECS · Redis para hot keys.
  • Particionamento: lake por data/canal; partition key sem hotspot; consumer groups paralelos.
  • Meta 10M+ tx/dia: capacidade-alvo do desenho (FinOps: custo/1M tx). Na mesa mostro o caminho e onde puxo a alavanca — não um load test de produção.
